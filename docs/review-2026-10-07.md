# Code review — 2026-10-07

The human asked: "do a code review of the project, build a plan to make sure we're not making huge
mistakes along the way, and fix any critical bugs." Scope: Station (`server/`, `shared/`), the portal
(`web/portal`), the Pi deployment (`deploy/raspberry-pi`), and the Scout, Outpost and shared firmware.
About 35k lines, reviewed by risk: security first (who can act as whom, over the web and the radio),
then data integrity, then robustness.

## 1. Fixed in this review

| # | Severity | What was wrong | Fix | Commit |
|---|---|---|---|---|
| 1 | **Critical** | **Radio requests trusted the sender's self-declared name.** A Waylink envelope's `src` is text the sender writes, and a Reticulum packet says nothing about who sent it. Anyone with a LoRa radio could act as any signed-in Scout: send unsigned messages and mail as its person, raise a camp-wide Beacon, post notices, edit Fieldbook, or unpair it. Since the Pi Station's Wi-Fi also carries Reticulum, a laptop on WAYPOST could do the same. | **Device keys.** At sign-in Station gives the device a random key, in a reply only that device can read. The device tags every request's `mid` with it: 8 random hex + 4-byte HMAC, so no packet grows (`shared/protocol/devauth.py`). Untagged requests are handled as coming from an unknown device. In production, bindings from before keys must sign in again; the Scout does this by itself. Pinned vector checked by Python and the Scout at boot. | `0284c1a` |
| 2 | **Critical** | **Pairing codes could be guessed.** Redeeming a 6-digit code needs no sign-in, and wrong guesses were unlimited and cheap. Over Wi-Fi, all million codes could be tried within a code's 10-minute life, binding an attacker's device to someone's account. | At most 20 wrong codes a minute across the Station (~35 days to search all codes). | `85c59d3` |
| 3 | High | **Catch-up could lose messages.** `MSG_SYNC` marked messages delivered when it *sent* the reply. A reply lost on the radio, or one that arrived after a retry and was dropped as stale, meant those messages never reached the Scout as new. They stayed in history, but unread. | Delivery is confirmed by the device: each `MSG_SYNC` acks the ids it stored, and unacked messages come again. Scout updated; older callers keep the old behavior. | `85c59d3` |
| 4 | High | **`MSG_SYNC` accepted unsigned copies "from" anyone.** A device could plant a message that appeared to be written by someone else. Uploading one's *own* copy crashed the handler: it paired the person with themselves. | Only the device's own person's messages are accepted (others' travel signed, by peer sync), filed in the message's own conversation. | `85c59d3` |
| 5 | Medium-high | **Uploads were buffered whole before the size check.** On a Pi 3 (<1 GB RAM), one huge upload could take Station down. | Caddy refuses >26 MB; the route reads at most limit+1 bytes. | `85c59d3` |
| 6 | Medium | **Backups copied the live database with `cp`**, which can be silently corrupt if Station writes mid-copy. | SQLite online backup plus an integrity check before keeping it. | `35933f1` |

Also fixed earlier the same week, while bringing the Pi up:
- Scout sign-in derived the key from an empty password.
- The "Station quiet" back-off blocked anything a person asked for.
- Station lost reply routes on restart.
- The CA certificate download returned 403.

Checked and found sound:
- Portal HTML escaping: every `innerHTML` build escapes user text.
- SQL: parameterized everywhere.
- Locker file names are stripped to their last part.
- Session cookies: HttpOnly, SameSite=Lax, Secure behind Caddy.
- Passwords: PBKDF2-SHA256, 200k rounds.
- The WHOAMI route-learning only applies to unbound devices, so routes can't be redirected.
- The web API's `owner` field is ignored when sign-in is required.

## 2. Open issues, in order

**P1: do before the camp relies on it**
1. **Outposts are still trusted by name** (claimed-Outpost ops: `BOARD_SYNC`, `CERT_LIST`, Corkboard). Spoofing one plants Corkboard notes. Give Outposts a device key at claim time, as Scouts get one at sign-in.
2. **Community key backup off the Pi.** Backups sit on the same SD card. If the card dies, the community key dies with it, and every device's trust anchor with it. Pull the nightly archive to another machine (or a USB stick), and practice a restore once.
3. **Who may raise a Beacon.** Any signed-in person can set off a camp-wide emergency alert (30 s cooldown). Decide whether that's intended or should need a role (Groups).
4. **Version reporting.** This week, several "it's broken" moments were really "the new code isn't running yet". Station (`/api/health`, Signal page), the Scout (Signal) and the Outpost should each show the git commit they run.
5. **Portal sign-in throttling.** Unlimited attempts. Each costs ~1 s of Pi CPU, so it's both a guessing and a load problem. Add a small per-address limit.

**P2: soon**

6. **Scout flash writes aren't atomic.** The store index, outbox, receipts and device key are overwritten in place, so a power cut mid-write can corrupt them. Write a temporary file, then rename.
7. **Unsigned paths remain** (unsigned `MSG_SEND` from verified devices, the portal). These are fine now that devices are verified, but roadmap D10 (everything signed) is the end state.
8. **Retire `firmware/pocket`** and fix the ~20 doc references to it.
9. **Rest of D6:** choose sync peers by capability, `CAPS_GET`.
10. **The Outpost Wi-Fi page doesn't sign delivery receipts** for messages read in the browser.

**P3: housekeeping**

11. `waypost.local` lookups are flaky from the laptop. The HTTPS certificate doesn't cover the Pi's LAN address.
12. Firefox and Edge on Linux need the CA imported separately; the trust page should say so.
13. Static pages get no `Cache-Control`, so browsers show stale portal pages after an update.

## 3. The plan: guardrails so mistakes are caught early

Most of this week's serious bugs share one pattern: **code that compiled and passed the Python tests,
but was only exercised on the hardware, where it failed in front of the human.** The empty-password
sign-in, the half-duplex reply loss and the quiet-mode lockouts all went that way. The guardrails
target that gap.

1. **Test the shared firmware code on the laptop.** `firmware/common/waypost_core` (CBOR codec, sync
   engine, certificates, objects) and the Scout's pure logic (devauth tags, store parsing) can run as
   host C++ unit tests against the same pinned vectors Python uses. Today they're checked only by a
   boot self-test on the device.
2. **A hardware smoke test after every flash.** Script what was done by hand this week, using the
   Scout's USB remote and Station's log: boot → sign in → PING → Trailhead page → send a message →
   catch-up → Look around sees Station and the Outpost. Run it before saying "done". Most of this
   week's bugs would have failed it in a minute.
3. **CI on every commit:** `pytest server/tests` plus `pio run` for scout and outpost. Today nothing
   runs automatically, so a broken build or test can sit unnoticed.
4. **A checklist for every new radio op:** who may call it, what proves it (device key, signed object
   or nothing), where the reply goes, does it fit one packet (size test), and what an unanswered retry
   does (is the operation safe to repeat). Items 1 and 3 in §1 would have been caught by the first and
   last questions.
5. **Know what's running.** Version reporting (P1 #4). Deploy code with `waypost-update`, and setup
   changes with the installer. Optionally, a sudo rule just for `waypost-update` so updates don't wait
   on a password.
6. **Data safety drill.** Off-device backup of the community key and database (P1 #2), and one real
   restore onto a spare SD card before camp.
7. **Keep the cross-language pinned vectors.** They caught nothing wrong this week, but they are why
   the Python/C++ boundary (keys, signatures, receipts, device tags) hasn't failed on hardware. Every
   new format gets one.

## 4. Deploying these fixes

Firmware: the Scout and the Outpost are flashed. Station needs `sudo waypost-update` on the Pi. After
that, Station requires device keys (production). The Scout notices Station no longer takes it as
signed in, signs in again on its own (its identity key is unsealed: no PIN), and receives its key.
The backup script and the Caddy upload limit take effect at the next full installer run.
