3. **Update this file** before you stop: current focus, what you changed, what’s blocked, what the other agent should do next.

### 2026-10-03 — Claude (found and fixed the real root cause of the Station TX-gap mystery — commit `e88bec5`)

**Re:** Human said Cursor had been working on Scout and the T-Deck was connected; asked me to dig into the Station TX gap now that two independent devices (Outpost, Scout) confirmed the same symptom.
**The actual bug, after weeks of this being blamed on the radio/RNode TX path:** `WaylinkGateway._loop()` (`server/gateway/waylink.py`) ran as a fire-and-forget `asyncio.Task` with **zero exception handling anywhere in its chain**. One unhandled exception while decoding a packet, running its handler, or sending the reply silently killed the *entire* receive loop — forever, for the rest of the process's life. Nothing ever surfaced it: asyncio only logs an unretrieved task's exception when the Task object is garbage-collected, and `gateway._task` lives in `app.state` for the app's whole lifetime, so that warning could never fire in production. This is the real explanation for "it worked once over real LoRa, then never again" — observed repeatedly by both of us across Outpost `BOARD_SYNC` and Scout `CORE/PING`, previously (wrongly) characterized as a Station RNode transmit/CSMA problem.
**How I found it:** added temporary return-value logging to `ReticulumTransport.send()` (`rns_packet.send()` returns `False` with no exception on failure — a real footgun in its own right, but not the bug here) and bumped the live Station's RNS log level to `LOG_PATHING`. Reset the Outpost and watched both sides simultaneously: Station's `rpc_received`/`rpc_send` logs for the Outpost's `BOARD_SYNC` appeared and completed cleanly, but a prior Scout `PING` attempt that had logged `rpc_received` never got a `rpc_send` or any debug line after it — and *nothing at all* showed up afterward, from either device, for minutes. Checked thread states (`/proc/<pid>/task/*/wchan`) — nothing was blocked on I/O, meaning the handling thread had already finished, which only makes sense if it raised before reaching my logging line.
